# S1.2 follow-up: built-in `inspect` diagnostic model

Owner-approved diagnostic scope addition (2026-10-05). The immutable product spec
(`docs/spec.md`) is unchanged; this note records the implementation findings and
any follow-up questions.

## Findings

- `inspect` is a built-in pseudo-model, not a new upstream CLI adapter. It is
  listed by `GET /v1/models` after the existing `passthrough` entry and is
  selectable with the same case-insensitive, trimmed matching used for real
  providers and `passthrough`.
- No provider YAML entry, binary or paid subscription is required. `inspect`
  works even when every real provider is disabled or missing.
- `POST /v1/chat/completions` with `model: inspect` returns the original HTTP
  request body text verbatim as `choices[0].message.content` inside a normal
  OpenAI completion envelope. The response `model` field is the canonical
  `inspect`.
- The echo preserves JSON whitespace, key order, escape spelling and unknown
  fields because the raw body bytes are used directly; they are not
  deserialized and reserialized.
- `inspect` is detected by a minimal pre-flight parse (`model` and `stream`
  only) before the stricter dictation validation. This lets it echo requests
  with multiple user messages, assistant/tool messages, unsupported content
  shapes and malformed `<transcript>` envelopes, all of which normal parsing
  would reject. Only valid JSON with `model` identifying `inspect` is required;
  malformed JSON still returns the existing text-free 400 errors and body
  size/time bounds remain enforced.
- `inspect` bypasses the busy guard, the fallback chain, prompt composition,
  cleanup and every AI CLI call. It returns immediately even when another
  formatting run is active or no provider is configured.
- `stream: true` uses the existing SSE framing and places exactly the same
  echoed body in the delta `content`. `stream` follows the same rule as normal
  requests: missing or `null` means `false`; a non-boolean value is rejected by
  the initial parse with the same text-free 400, with no broad API changes.
- Ordinary metadata logging stays text-free and gains a `kind=inspect` entry.
  The opt-in debug log records the exchange as usual, including the request
  body and the echoed response, with credential-bearing headers redacted.
  `inspect` itself is a diagnostic response, not a log: it does not add new
  logging beyond the existing metadata and debug sinks.

## Questions for the owner

- Owner approved this diagnostic scope addition explicitly (2026-10-05). No
  further product change is requested at this time.
- If header diagnostics become useful later, they are outside the current
  JSON-body scope; adding them would require a deliberate scope decision
  because the design deliberately excludes credential-bearing headers.
