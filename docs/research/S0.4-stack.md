# S0.4 — Validate the stack

Scope: confirm with a minimal prototype that Rust fits Pumice. That means:

- a single executable with no runtime dependencies;
- spawning `claude -p` in an empty temp directory;
- CI builds on Windows, Linux and macOS, with a statically linked C runtime on Windows.

It also records the route to an installer and auto-update with Tauri for Phase 3 (research only). Date: 2026-10-03.

## What was built

A Cargo project at the repo root (package `pumice`, edition 2024, Rust 1.99 stable) with one binary and two prototype subcommands.

| Path | Purpose |
| --- | --- |
| `Cargo.toml` | Dependencies: `serde_json` and `tempfile` only. Release profile: `lto`, `codegen-units = 1`, `strip`. |
| `.cargo/config.toml` | `+crt-static` for `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc` |
| `src/http.rs` | Minimal HTTP/1.1 request parsing over `std::net`: `Content-Length` and chunked bodies, 10 MiB cap, header redaction |
| `src/listen.rs` | `pumice listen`, the logging listener for S0.1 |
| `src/probe.rs` | `pumice claude-probe`, the stack check |
| `src/time.rs` | RFC 3339 timestamps using only `std` |
| `tests/listener.rs`, `tests/probe.rs` | Raw-TCP listener tests and fake-CLI probe tests |
| `.github/workflows/ci.yml` | 3-OS matrix: fmt, clippy, test and release build; a Windows CRT DLL check; binaries uploaded as artifacts |

There is no async runtime, HTTP framework or argument-parsing crate. That kept the prototype small: the release binary is 556 KB on Linux. Phase 1 can pick a proper HTTP stack.

### `pumice listen --port <PORT> [--reply-prefix <TEXT>] [--log-file <PATH>]`

- Binds `127.0.0.1` only. `--port` is required; the default port is still an open decision (S1.5). If the port is taken, it exits 1 with a clear message.
- Accepts any method on any path. For each request it logs the time, the remote address, the request line, every header (`Authorization` and any header with `key` or `token` in its name show as `<redacted, N chars>`), and the body (pretty-printed when it is JSON).
- `GET …/models` returns a one-model list (`pumice-echo`).
- `POST …/chat/completions` echoes the last `user` message back. The content can be a string or an array of text parts. With `stream: true` the reply is OpenAI-style SSE (`chat.completion.chunk` events, then `data: [DONE]`); otherwise it is a `chat.completion` JSON object.
- Every response sends `Connection: close`. Reads time out after 30 s.
- **The listener logs the dictated text on purpose.** It is a research tool for S0.1. The Phase 1 server must follow security rule 5 and not log dictation unless debug logging is on.

### `pumice claude-probe [--text <TEXT>] [--claude-bin <PATH>] [--timeout-secs <N>]`

- Spawns `claude` with its working directory set to a fresh `tempfile::tempdir()`, which is removed afterwards.
- Arguments: `-p --safe-mode --restricted --disable-slash-commands --output-format json --tools "" --strict-mcp-config --no-session-persistence --system-prompt <prompt>`. `--tools` gets a real empty-string argument.
- The dictation goes to **stdin**, never into argv.
- stdout and stderr are drained on separate threads. A 30 s timeout polls `try_wait` and then kills the child.
- It reads the JSON envelope. A non-zero exit **or** `is_error: true` counts as a failure, and the message from the envelope is shown, because Claude prints "Not logged in" on stdout, not stderr (see S0.2). Spawn `NotFound` is reported as "claude is not installed or not on PATH".

The fake-CLI tests check that the probe passes `-p`, an empty `--tools` argument, `--strict-mcp-config` and a system prompt. They also check that it runs in an empty directory, sends the text on stdin, times out and kills a hanging CLI, and surfaces both a stderr failure and an `is_error` envelope. They are `#[cfg(unix)]` because the fake CLI is a shell script. On Windows only the "not installed" test runs. A cross-platform fake CLI (a small Rust test binary) belongs to S8.2.

## Known limitations (for Phase 1)

- **Windows `.cmd` shims:** `Command::new("claude")` only finds `claude.exe`. If a CLI is installed as a `.cmd` or `.ps1` shim (common with npm installs), Pumice has to resolve it explicitly, without going through a shell, so the dictation can't be interpreted as a command. Noted in `src/probe.rs`.
- **Killing on timeout:** `Child::kill` kills only the direct child. Grandchildren (for example Node workers) can outlive it. The prototype detaches its pipe-reading threads so the timeout still holds. Phase 1 should kill the whole process tree: a Job Object on Windows, a process group on Unix.
- **Probe output** is printed without the debug-log switch. That is acceptable for a manual tool, not for the server.

## Phase 3: installer and auto-update with Tauri (research only)

Source: [Tauri v2 updater plugin](https://v2.tauri.app/plugin/updater/), accessed 2026-10-03.

- **Bundles:** the Tauri v2 bundler produces NSIS (`-setup.exe`) and MSI installers on Windows, `.app`/`.dmg` on macOS, and AppImage/deb/rpm on Linux. Pumice could ship as a Tauri app with a tray icon, running the existing Rust server in-process. Or Tauri could install and supervise the plain `pumice` binary as a sidecar. The spec rules out a GUI, so the Tauri layer would be installer plus tray only. That is a decision for Phase 3.
- **Updater (`tauri-plugin-updater`):**
  - Signature checking is mandatory and can't be disabled. Generate a key pair with `tauri signer generate`, put the public key in `tauri.conf.json`, and pass the private key at build time as `TAURI_SIGNING_PRIVATE_KEY`. If the private key is lost, existing installs can't be updated.
  - Updates come from a static `latest.json` (`version` plus a signed URL per platform). GitHub Releases works through `https://github.com/<owner>/<repo>/releases/latest/download/latest.json`, and the Tauri GitHub Action can generate it.
  - On Windows the NSIS/MSI installers are the update packages. `installMode: passive` (the default) shows a small progress window and needs no clicks. The app is force-quit during the install.
  - It is desktop-only and needs Rust 1.77.2 or later.
- **Fit with the current stack:** the `+crt-static` setting and the dependency-free binary carry over. Tauri's WebView2 dependency on Windows ships with Windows 11 and can be bundled for Windows 10. That is a runtime dependency to weigh against the "no runtime dependencies" rule, so the open question is under **Questions for the owner**.
- **Lighter alternative:** a self-updating plain binary (download, verify the signature, swap) without Tauri, plus an NSIS or WiX installer built in CI. Less tooling, but the signing and swap logic would be ours.

## Findings

- **Rust fits.** A single static binary, about 0.5 MB on Linux, using only `std` networking. It has 2 direct dependencies and needs no runtime on the user's machine.
- **The Claude path works end to end from Rust:** non-interactive, with no tools, in an empty temp dir, text on stdin. The real call took 2.8 s, inside the 30 s target. Together with S0.2 this meets the second Phase 0 gate condition.
- **Treat Claude's JSON envelope as the source of truth.** `is_error: true` with exit 0 or 1, and errors printed on stdout, mean exit code and stderr alone are not enough.
- **The Windows executable has no runtime dependencies.** With `+crt-static` it imports only Windows system DLLs (kernel32, ntdll, ws2_32, bcryptprimitives, and the api-ms-win-core synch API set). CI checks this on every build.

## Questions for the owner

1. **Is WebView2 acceptable for Phase 3?** The spec says "No runtime dependencies for end users." Tauri needs WebView2 on Windows; it ships with Windows 11 and can be bundled for Windows 10. Is that acceptable, or should Phase 3 use a plain signed installer plus self-update instead?
2. **Windows `.cmd` shims:** if `claude` is installed through npm on Windows, it is a `.cmd` shim. Should Pumice support that from v0.1 (explicit resolution without a shell), or document "native installer only"?
