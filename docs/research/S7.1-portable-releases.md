# S7.1 — Portable release builds

Research note for story S7.1 (portable release builds). Findings from official
sources, checked 2026-10-05.

## Findings

### Distribution approach (owner decision, 2026-10-05)

The owner authorized a revised, easy distribution path: release binaries
attached to GitHub releases, plus npm packaging in a follow-up story. This
replaces the spec's Phase 3 Tauri-based installer/auto-update path, which
stays deferred. The owner canceled the earlier distribution PRs (#33 archives,
#34 changelog and #35 action maintenance, all still closed) and subsequently
chose this narrower distribution scope; this implementation is a fresh, deliberately small scope:
build → verify → archive → artifact preview. No publishing, no tags.

### Targets and runners

| Target | Runner | Archive |
| --- | --- | --- |
| `x86_64-unknown-linux-musl` | `ubuntu-latest` (x64) | `.tar.gz` |
| `x86_64-pc-windows-msvc` | `windows-latest` (Windows Server 2025) | `.zip` |
| `x86_64-apple-darwin` | `macos-15-intel` (macOS 15 x64) | `.tar.gz` |
| `aarch64-apple-darwin` | `macos-15` (macOS 15 arm64) | `.tar.gz` |

Runner labels verified against the official
[actions/runner-images](https://github.com/actions/runner-images) README:
`macos-15-intel` is macOS 15 on Intel x64, `macos-15` is macOS 15 on arm64.

- The musl target produces a fully static Linux executable; `musl-tools` is
  installed with apt **only** on the Linux musl runner. The static link is
  verified with `readelf`: no dynamic interpreter or required shared libraries.
- Windows already links the C runtime statically via
  `.cargo/config.toml` (`+crt-static`). The release workflow locates
  `dumpbin.exe` through `vswhere.exe` (shipped with Visual Studio) and checks
  the exe has no `vcruntime`/`msvcp`/`ucrtbase`/`api-ms-win-crt` dependency.
  `ilammy/msvc-dev-cmd` is intentionally not used: it still pins an old Node
  runtime, and the build itself does not need its environment (same as ci.yml,
  which uses it only for dumpbin today).
- macOS builds run on native matching-architecture runners, so no
  cross-compilation or SDK juggling is needed.

### Action versions

Verified against the official action repositories (latest releases):
`actions/checkout@v7` (v7.0.1), `actions/upload-artifact@v7` (v7.0.1),
`actions/download-artifact@v8` (v8.0.1), `actions/setup-python@v7` (v7.0.0).
These run on the current Node runtime. The existing `ci.yml` still pins older
majors (`checkout@v5`, `upload-artifact@v5`); updating it is a separate change
and was intentionally left out of this story.

Note: `upload-artifact` v6+ uploads matched files flat (leaf names only),
which is what the checksum job relies on — archives land in one directory by
basename.

### Version extraction

`scripts/package_release.py` reads `[package].version` from `Cargo.toml` with
Python's stdlib `tomllib` (Python ≥ 3.11, pinned in the workflow via
`setup-python`). The workflow smoke-tests both the raw and the packaged
binary with `--version` and asserts it matches the Cargo version. The binary
prints `pumice <version>` (`env!("CARGO_PKG_VERSION")`).

### Helper and archive layout

The packaging helper (`scripts/package_release.py`) is development-only,
stdlib-only, and whitelists: supported target triples, the version from the
repo's Cargo.toml, an existing release binary, and exactly four packaged
files (`pumice`/`pumice.exe`, `LICENSE`, `pumice.example.yaml`,
`scripts/INSTALL.md` copied in as `INSTALL.md`). It rejects anything else,
never walks the repository or `target/`, and never touches the test-only fake
CLI. Executable mode is preserved on Unix (tar modes; zip external attributes).
Each archive has one top level: `pumice-{version}-{target}/`.

The workflow is triggered by `workflow_dispatch` and by pull requests that
touch release-related paths only; every job has `permissions: contents: read`
(the minimum); artifacts are kept 7 days. A `checksums` job downloads the four
archives, emits `SHA256SUMS` (basenames only) and re-uploads everything as a
single `release-preview` artifact. Nothing is published and no tags are
created.

### Manual release path (for the owner)

Once the preview artifacts from a dispatched run look right, a real release
is manual, e.g.:

```sh
gh release create v0.1.0 --draft --title "v0.1.0" \
  dist/pumice-0.1.0-x86_64-unknown-linux-musl.tar.gz \
  dist/pumice-0.1.0-x86_64-pc-windows-msvc.zip \
  dist/pumice-0.1.0-x86_64-apple-darwin.tar.gz \
  dist/pumice-0.1.0-aarch64-apple-darwin.tar.gz \
  dist/SHA256SUMS
```

Review the draft in the GitHub UI before publishing. There is deliberately no
publishing workflow yet.
