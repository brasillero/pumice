## 1. Entry point, modules and process boundaries

**Recommend hybrid dispatch:** `pumice` is the product orchestrator now; relay and formatter subcommands call their library CLI entry points in-process, while transcription subcommands launch its independent executable. Full-stack operation runs relay and transcription in separate processes and imports the pure formatter library. This revises round 1's default-command recommendation (`docs/research/architecture-modules.md:9`, `:253`).

```text
pumice                                    orchestrator serve; see compatibility below
pumice serve [--stack-config FILE]         serve the configured stack
pumice run AUDIO --flow ID [--stack-config FILE]
pumice relay [serve|request|doctor|check-config|models|status|health|capabilities] …
pumice transcribe [file|serve|doctor|check-config|models|backends|status|health|capabilities] …
pumice format [apply|list|show|doctor|check-config|status|health|capabilities] …
pumice config validate [--stack-config FILE] [--json]
pumice config migrate --module relay [--from FILE] [--to FILE] [--dry-run] [--json]
pumice status|health|doctor|capabilities [--stack-config FILE] [--json]
pumice --help|--version [--json]
```

Canonical examples: `pumice relay serve --plain --config relay.yml`, `pumice transcribe file clip.wav --model turbo`, `pumice format apply --formatter ID --request -`. `pumice relay` defaults to relay serve. Module `--config` always belongs to that module; `--stack-config` belongs to orchestration. Model management is under `transcribe models`; relay `models` lists configured provider routes, never downloads AI models. Formatter lists definitions rather than pretending they are models.

Use a Cargo workspace with libraries and thin binaries: `crates/relay` → `pumice-relay`, `crates/transcription` → `pumice-transcribe`, `crates/formatter` → `pumice-format`, `crates/orchestrator` → `pumice`. Shared wire/output/config helpers must contain no provider or native-engine types. Keep root `[package]` during extraction until packers can read workspace versions (`scripts/package_release.py:43`). Cargo's [workspace reference](https://doc.rust-lang.org/cargo/reference/workspaces.html) documents shared lockfiles and member selection.

All three module executables remain independently usable. Relay's executable includes its entire relay implementation and requires neither `pumice` nor transcription sidecars. `pumice relay …` invokes the same relay library argument handler, not a second implementation. Formatter follows that pattern. `pumice transcribe …` forwards OS arguments/stdio to an explicitly configured executable, else the trusted install-relative transcription bundle; no shell, cwd or arbitrary PATH fallback. Return the child's exit status and forward cancellation. Missing/incompatible transcription produces a typed installation error, never an automatic install.

For managed stack relay, spawn the absolute current `pumice` executable with `relay serve` in private managed mode; allow a configured `pumice-relay` instead. Thus the lightweight core needs only `pumice`, while its running relay is still process-isolated. Managed transcription is always `pumice-transcribe`. Match wire protocol/capabilities before readiness; never launch through the npm JS shim. External loopback components are explicit and never owned or stopped by the orchestrator.

Trade-offs: hybrid dispatch preserves single-file core upgrades and today's npm footprint, but needs parity tests between standalone and subcommand adapters. Uniform sibling execution is simpler conceptually but breaks users who copy only today's executable and makes relay use depend on another installed file. Linking transcription in-process couples native failures/DLLs to the relay and conflicts with D1/D2. No transcription dependency or feature enters the relay/core build graph (`docs/research/architecture-modules.md:190`, `:198`).

Keep relay Linux static musl and Windows static CRT checks; macOS uses only OS libraries, not a promise of fully static macOS. Transcription has separate native bundles/manifests and GPU prerequisites. Sharing a repository or CLI brand does not imply sharing native linkage (`.github/workflows/release.yml:115`, `:127`; `docs/research/architecture-modules.md:235`).

## 2. Concrete migration and compatibility window

Current version is 0.2.0 (`Cargo.toml:3`). Recommend **0.3.0** for the orchestrator/config transition, preceded by 0.3.0 alpha previews; never disguise this as a patch. Under [SemVer §4](https://semver.org/#spec-item-4), 0.y.z is initial development; the minor transition is this project's migration policy, not a SemVer guarantee of compatibility. Keep one coordinated module release version initially, plus independently versioned machine/wire schemas.

| Form | 0.3.x and 0.4.x | 0.5.0, earliest removal release |
| --- | --- | --- |
| Bare `pumice` / `pumice serve` | Orchestrator reads `orchestrator.yml`; if absent, its compatibility profile supervises only relay with today's config, port and display behavior; warn once | Require an explicit orchestrator config; missing file returns configuration error and migration guidance |
| `pumice --plain`, root `--config FILE`, legacy `serve --plain/--config` | Unambiguous deprecated dispatch to relay serve; supplied FILE is relay YAML even if a stack config exists | Reject with exact replacement command |
| `pumice check-config [--config FILE]` | Deprecated relay validation alias | Use `pumice relay check-config` |
| `pumice doctor` and its old flags | Deprecated relay doctor alias; aggregate doctor requires `--stack-config FILE` during this window | Root doctor becomes aggregate; use `pumice relay doctor` for providers |
| Default `pumice.yaml` lookup | Relay reads it only when `relay.yml` is absent, with warning | Stop automatic old-name lookup |
| Explicit `pumice relay … --config old-name.yaml` | Read the specified relay file; warn for `pumice.yaml` | Continue supporting arbitrary explicit filenames; the old schema is still valid |

No-config compatibility also preserves today's no-provider defaults, `passthrough` and `inspect`; it never enables transcription, formatter or an AI provider. Invalid/present `orchestrator.yml` fails, rather than quietly selecting the compatibility profile. Legacy flags force relay mode; new stack configuration cannot hijack an existing `pumice --plain` service. Do not reuse root `--config` for orchestration until aliases retire; retain `--stack-config` thereafter.

The earliest removal is 0.5.0, **only after migration is documented and the owner has verified the server deployment**. Delay removal if that gate is unmet. These are proposed windows requiring owner approval, not permission to remove compatibility now.

## 3. Config ownership, paths and validation

Recommend `relay.yml`, `transcribe.yml`, `formatter.yml`, `orchestrator.yml`. Relay keeps today's root YAML schema; new modules use `schema_version: 1`. Formatter definitions are explicitly registered files, not extra module configuration files. The orchestrator owns component locations/ownership, flows, frontend and flow budgets; module files own providers, model/backend settings or formatter definitions (`.task-decisions/tasks/arch-modules/decisions.md:94`).

| Platform | Config directory | Managed model data directory |
| --- | --- | --- |
| Windows | `%APPDATA%\pumice` | `%LOCALAPPDATA%\pumice\models` |
| Linux | Absolute nonempty `$XDG_CONFIG_HOME/pumice`, else `~/.config/pumice` | Absolute nonempty `$XDG_DATA_HOME/pumice/models`, else `~/.local/share/pumice/models` |
| macOS | Same XDG/`~/.config/pumice` rule as today | `~/Library/Application Support/pumice/models` |

Keep macOS config lookup unchanged to avoid a second migration; adopting Application Support for configs adds no value now. Existing platform lookup is `src/config/mod.rs:429`, `:456`. New model directories are **UNVERIFIED proposals**, with `models_dir` override in `transcribe.yml`; reject unusable/missing platform bases rather than falling back to cwd. Models/configs live outside install/npm directories.

Lookup: explicit module `--config` wins and missing files fail; otherwise the per-user module filename. For relay only, absent `relay.yml` allows same-directory `pumice.yaml` during the window. If both exist, choose `relay.yml` and warn that the old file is ignored; never merge them. Read/parse/permission errors in the preferred file fail without fallback. No automatic cwd, executable-directory, env-setting or multi-directory search. Missing standalone relay config retains built-in defaults; other module serve/flow commands require their explicit enabling configuration.

`orchestrator.yml` lookup is explicit `--stack-config`, then the per-user file. Managed components must specify config paths, resolved relative to this file; the orchestrator never silently discovers another module config. A disabled component is never launched. Formatter config is an explicit reference. External components specify a loopback URL instead of a locally owned config. Resolve each module's model/definition/log/binary paths against its own config, matching relay's existing anchoring (`src/config/mod.rs:125`, `:157`). No module settings are copied into the orchestrator file.

Migration command: validate the source as relay YAML; default source/destination are per-user `pumice.yaml`/`relay.yml`. `--dry-run` reports actions; execution copies bytes into a private temporary file, validates, then installs without clobbering. Same-directory copy preserves comments and relative settings; retain the source for rollback. Reject existing destination, symlink destination, and cross-directory migration in v1 rather than silently changing path semantics. Migration never edits services or generates/enables a stack config. Repeating an already completed identical migration reports no-op; differing destination requires manual resolution.

Every module offers `check-config --json`; `pumice config validate` aggregates managed config validation through each module's validation contract. Preserve original file/line/column, including referenced definitions; reject unknown keys/duplicate IDs/references and ambiguous managed/external declarations. Validation launches no AI CLI or inference, downloads nothing, and needs no GPU initialization. Distinguish syntax validity from readiness; unavailable module validator produces a typed validation-unavailable error, not a claim of success. Local model existence/hash verification is explicit `models verify`. Current located errors: `src/config/mod.rs:461`.

## 4. Transcription delivery: CPU, dispatch, GPU and downloads

D8 has already superseded the AVX2-only policy; it is not an open question (`.task-decisions/tasks/arch-modules/decisions.md:109`, `:115`). CPU-first is a releasable increment, not the final scope. Reuse the transcribe-cpp 0.3.1 spike initially, pending the engine choice below; four-target CPU CI is reported at `S:docs/research/S10.1-transcription.md:120`. Real baseline/non-AVX2 execution, GPU behavior and Windows UTF-8 correctness remain **UNVERIFIED**.

1. **Plain CPU:** portable baseline host with explicit local model/audio, bounded WAV decode, one model/one inference, fake-engine seam. No global AVX2/native CPU compiler flags. Keep a portable CPU archive even after acceleration ships; publish measured limitations rather than exclude old CPUs.
2. **Runtime CPU selection:** on x86 ship baseline plus accelerated CPU variants with the matching core/ggml libraries. Selection checks hardware/OS capabilities before loading optimized code; ARM retains its portable CPU path and only verified relevant variants. Variant support in pinned source is reported at `docs/research/architecture-modules.md:210`; packaged behavior is **UNVERIFIED**. Missing/incompatible packs must still leave the tested baseline path available.
3. **GPU:** Windows Vulkan first, macOS arm64 Metal, then Linux GNU/glibc Vulkan; each its own packaging/validation PR. macOS Intel stays CPU until Metal is verified there. CUDA is a later explicit NVIDIA pack after demand/benchmarks and runtime licensing/driver checks; never the universal prerequisite. The pinned Handy matrix provides precedent, not Pumice validation ([source](https://github.com/cjpais/Handy/blob/a42131d24c59315fede06775cd354219c4f4a87b/src-tauri/Cargo.toml#L130); `docs/research/architecture-modules.md:214`, `:221`).

Manifest each native bundle: product/engine/ABI version, target/libc floor, features, file hashes and licenses. Load native code only from its trusted installation directory, never cwd/request paths. Native executable/libraries update atomically as one versioned directory; preserve prior bundle and models for rollback. Linux accelerated bundles are separate GNU assets; keep static musl CPU assets independent (`docs/research/architecture-modules.md:212`, `:223`, `:237`). No developer SDK/runtime is required by the end user; GPU OS drivers are prerequisites ([Vulkan loader guide](https://docs.vulkan.org/guide/latest/loader.html)). Keep Windows static CRT for Rust and CMake unless the owner separately approves a transcription-only exception; DLL-boundary feasibility is **UNVERIFIED**.

Expose `backends list --json`, backend capabilities and selected backend/device/CPU variant in readiness/status. `backend=auto` selects only shipped compatible backends during initialization and may choose CPU if GPU initialization is unavailable; explicit backend requests fail if unavailable. Never retry a failed inference on another backend invisibly. Changing backend packs/model selection requires a controlled module restart. CPU correctness, clean-machine dependency closure and driver-free startup precede advertising GPU acceleration; real-device correctness/performance requires owner hardware checks.

**Downloader belongs to transcription**, authorized by D9 (`.task-decisions/tasks/arch-modules/decisions.md:124`, `:130`):

- Ship an offline versioned catalog with ID, engine compatibility, immutable source revision, exact filename/HTTPS URL, SHA-256, byte size and license/provenance. Pin actual bytes, not `main` or a mutable model alias; no catalog row until hash/license are verified.
- Commands: `models list --source catalog|installed|all --json`, `models download ID --json`, `models register ID --path FILE`, `models verify ID --json`. Downloads populate storage but **do not enable a model/config entry**. Startup, readiness, validation and inference never download; missing models report a corrective command. User local files remain supported/read-only and are never deleted by managed cleanup.
- Store verified managed files under the data directory, keyed by digest, with metadata and `.part`/resume sidecars; lock per digest. Download only catalog-approved HTTPS hosts/redirects, without sending AI credentials or accepting URLs from inference requests.
- Resume with byte ranges only if revision plus ETag/size still match; if the server ignores ranges or identity changes, restart safely. Rehash the complete file, verify size and SHA-256, then atomically rename on the same filesystem. Disk-full/hash/network errors retain no installed-model success state. Cancellation preserves resumable partial state; explicit cleanup affects only managed partials.
- Reuse the same service from CLI and future API/UI jobs. JSONL events report operation ID, model ID, downloaded/total bytes, state and safe error code; never fabricate a percentage without a known total. Bounded retry/backoff is allowed for download transport, not AI calls. A future explicit `POST /pumice/v1/models/downloads` returns a job ID with status/events/cancel routes; it must call this service rather than implement a second downloader.

Catalog hashes, hosting behavior, resumability and pack redistribution are **UNVERIFIED until fixture/HTTP-fake and real-source checks**. No external downloads are needed in automated tests. D10 does not authorize implementing a GUI, capture or hotkeys now.

## 5. Shared machine/UI conventions

Introduce a narrow versioned output/event contract once; module/domain logic stays in its library. UI calls those CLI/API services, not YAML parsers, CPU selectors or download implementations of its own (`.task-decisions/tasks/arch-modules/decisions.md:139`).

- Without `--json`, retain human output/TUI where appropriate. `--json` disables ANSI/TUI. One-shot stdout is exactly one result/error envelope: `{schema_version:1, operation_id, module, ok, result|error}`; exit status agrees with `ok`. `error` has stable code, retryability and config location where relevant. Only an explicit result contains dictated text; progress/logs never do.
- Under `--json`, stderr contains only JSONL metadata events: `schema_version`, `operation_id`, sequence, module/stage, event type and safe payload. Start, progress, warning and terminal events share operation IDs. Successful one-shot stdout has the final result; failures have one error envelope. Streaming/service commands use JSONL stdout events with `started/ready/status/stopped/error` rather than a final one-shot document. Document this distinction in capabilities.
- Native callbacks/diagnostics must be suppressed or sanitized before those streams; no uncontrolled child/native stderr mixed with JSONL. Plain logs remain on stderr. Limit/coalesce progress events; disconnected UI/event consumers must not block compute. Compatibility commands retain today's listening line and exit behavior unless `--json` is explicitly requested (`src/main.rs:363`).
- Exit **0** success; **2** invalid arguments/config/input; **1** runtime/network/backend/provider failure or unmet readiness; **130** explicit cancellation where supported. Preserve existing signal semantics for legacy paths. JSON codes carry detail; no UI parses human error strings or guesses HTTP status from exit 1 (`src/main.rs:128`, `:136`).
- `status --json` returns a snapshot without starting/stopping anything. `health --json` exits nonzero when the requested readiness condition fails. `doctor` performs local diagnostics only by default; relay's existing paid `--login-check` remains an explicit opt-in (`docs/install.md:118`). A pure formatter reports validity/availability rather than implying a daemon exists.
- Serving modules retain/add `/health` for liveness and `/ready` for readiness; versioned `/pumice/v1/status`, `/capabilities` and metadata events expose actual supported operations. Relay readiness checks local availability, not subscription login/quota. Existing relay `/health` remains compatible; transcription readiness includes a loaded selected model/backend. Aggregate readiness reports components and flows separately.

Keep OpenAI-compatible chat, transcription and model-list contracts. Formatter transforms requests via system-message injection; it never claims its output request is a completion. Combined audio→formatted-result flows use `/pumice/v1/dictations`, preserving raw transcript separately from final result; these later contracts require owner review (`docs/research/architecture-modules.md:73`, `:93`, `:99`).
