# S7.5 — generated changelog and release preparation

## Findings

Release notes are build-time output from the repository's Conventional Commits. git-cliff 2.14.2 is pinned for repeatable tooling. The initial committed changelog contains an Unreleased snapshot only: Pumice has no release tags yet, and the current Cargo version (0.1.0) is not evidence of a published release.

Use a checked-in Keep a Changelog template, offline mode and disabled external preprocessing commands. Features/fixes appear under Added/Fixed; compatibility changes remain visible even when an ordinary maintenance commit would be filtered. [Configuration](https://git-cliff.org/docs/configuration/git/).

Release preparation takes an explicit version matching Cargo and an explicit UTC date. git-cliff can generate a proposed version without creating a tag; its JSON context permits fixing the date before rendering. [CLI arguments](https://git-cliff.org/docs/usage/args/), [context loading](https://git-cliff.org/docs/usage/load-context/).

The prepared version section is reused byte-for-byte as release-notes.md and in the full prepared CHANGELOG.md. Existing released sections remain unchanged. Future GitHub release notes and Tauri's updater notes should consume that same generated text rather than independently rendering variants. This story prepares artifacts only; release publication, version tags and updater signing are separate reviewed actions.

The preview workflow has read-only repository permissions and uploads artifacts without publishing. Its date defaults to the HEAD commit date in UTC, making identical inputs repeatable. After a public release, Cargo must advance before another preview is prepared; existing versions/tags are deliberately rejected.
