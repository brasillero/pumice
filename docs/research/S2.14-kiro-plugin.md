# S2.14 — Kiro plugin (`kiro-cli`)

Owner request (2026-10-10): a new provider plugin for the AWS Kiro CLI,
provider id `kiro`, written from scratch. The archived S2.9 adapter, its tests,
fixtures and research note were deleted unread in the first commit of this
story; nothing here comes from them.

Installed version checked: `kiro-cli 2.29.0` (WSL, Linux x86-64), logged in
with IAM Identity Center. Sources: `kiro-cli --help`, `kiro-cli chat --help`,
`kiro-cli agent --help`, the official docs ([Headless mode][headless],
[Agent configuration reference][agent-ref], [Exit codes][exit-codes],
[Reasoning effort][effort], [Installation][install]) and the live checks
below.

## Invocation

```text
kiro-cli chat --agent-engine v2 --no-interactive --output-format stream-json \
  --trust-tools= --agent pumice --model <model> --effort low
```

run in the call's fresh temporary directory, with the user message on stdin
and one workspace file, `.kiro/agents/pumice.json` (see below). The child also
gets `KIRO_DISABLE_TELEMETRY=1` and `KIRO_NO_AUTO_UPDATE=1`.

| Piece | Why |
| --- | --- |
| `chat --no-interactive` | Headless mode ([headless]): one instruction in, the run ends after the turn |
| `--agent-engine v2` | Pinned, so a change of the CLI's default engine cannot change behavior. V2 is the 2.x default ("the pre-3.0 default" in `--help`). See [Engine choice](#engine-choice) |
| `--output-format stream-json` | The run's ACP events as JSON Lines on stdout; logs and warnings go to stderr. Works only on V2/V3 |
| `--trust-tools=` | "trust no tools" (`chat --help`). In non-interactive mode an untrusted tool call is denied, not asked |
| `--agent pumice` | The one-off agent file Pumice writes into the workspace (below) |
| `--model <model>` | From the user's YAML. V2 overrides the agent's and the saved model with it |
| `--effort low` | Cheapest settings (owner rule). See [Effort](#effort) |
| stdin | "When stdin is piped and there is no positional argument, Kiro reads the full stream as the instruction" ([headless]). No argv size limit, and the dictation never reaches argv |
| `KIRO_DISABLE_TELEMETRY=1` | Variable present in the 2.29.0 binary next to the legacy `Q_DISABLE_TELEMETRY` (AGENTS.md: no telemetry). Its effect was not measured |
| `KIRO_NO_AUTO_UPDATE=1` | Variable present in the binary; no update checks from runs Pumice starts. Its effect was not measured |

Nothing else is set or removed: the user's own login, settings
(`~/.kiro/settings/cli.json`), API key (`KIRO_API_KEY`) and `KIRO_HOME` are
inherited. Pumice never reads or writes `~/.kiro`.

## The agent file (approved exception to AGENTS.md security rule 3)

Kiro has no `--system-prompt` flag. The documented way to give a system prompt
is a custom agent's `prompt` field ([agent-ref]). `kiro-cli agent --help`:
"local agents are only discovered if the command is invoked at a directory
that contains them", so the file must be inside the working directory. The
owner approved this exception (2026-10-10): Pumice writes exactly one file,
`.kiro/agents/pumice.json`, into the call's fresh temporary directory
(directories 0700, file 0600, removed with the temporary root):

```json
{
  "name": "pumice",
  "description": "Answers one message without tools.",
  "prompt": "<the client's system prompt, verbatim; empty when it sent none>",
  "tools": [],
  "allowedTools": [],
  "mcpServers": {},
  "includeMcpJson": false,
  "resources": [],
  "hooks": {}
}
```

* `tools: []` gives the agent no tools at all; `allowedTools: []`
  pre-approves none; `mcpServers: {}` and `includeMcpJson: false` add no MCP
  servers and do not merge `mcp.json`; `resources: []` loads no files;
  `hooks: {}` runs no hook commands.
* An empty `prompt` is accepted (live call 3), so Pumice sends the client's
  system prompt as is, including an empty one (Handy sends none). Kiro's own
  built-in instructions stay underneath it: about 3.6 % of a 200k context
  before the first message (live calls), which Pumice cannot remove.
* **`file://` prompts are refused.** The `prompt` field also accepts a
  `file://` URI, which Kiro reads from disk ([agent-ref]). A client system
  prompt starting with `file:` (ignoring leading whitespace and case) would make
  the CLI read a local file into the model's context, so the plugin refuses
  such a request with `UnsupportedSystemPrompt` instead of writing it (security
  rule 4: Pumice never acts on request content).
* The name is fixed. A workspace agent wins over a global agent with the same
  name: with `KIRO_HOME` pointed at a scratch directory holding a global
  `pumice` agent, `kiro-cli agent list` in a workspace with a local one printed
  `WARNING: Agent conflict for pumice. Using workspace version.` and listed the
  workspace agent. A user's own global `pumice` agent therefore cannot replace
  the no-tools one.
* `kiro-cli agent validate` exits 0 for this file but also for unknown fields,
  so it proves nothing about field support; the live calls do.

## Output format (V2 `stream-json`)

One JSON object per line, `{"type": …, "data": …}`. Seen in the live calls:

| `type` | Meaning | Plugin |
| --- | --- | --- |
| `runStarted` | `data.payloadSchema: "acp"`, `data.engine: "v2"` | Required first |
| `metadata` | Session id, context usage, `reasoning.effortLevels`, credits used | Ignored |
| `sessionUpdate` | ACP `session/update`: `data.update.sessionUpdate` is `agent_message_chunk` (text in `content.text`), or `agent_thought_chunk`, `tool_call`, `tool_call_update`, … | Text chunks concatenate into the answer; every other update is ignored (owner decision 2026-10-08: tool records are not policed) |
| `runFinished` | `data.status: "success"`, `stopReason`, `finalText`, `finalTextTruncated` | Required, with `status: "success"` |
| `runError` | `data.stage`, `data.message` (free text), exit code 1 | Failure |

The answer is the concatenation of `agent_message_chunk` texts, which is
exactly `runFinished.finalText` in every live call. `finalText` itself is not
used because it can be truncated (`finalTextTruncated`). Unknown event types
are ignored; success still needs both `runStarted` and a successful
`runFinished`.

## Errors

Exit codes ([exit-codes]): 0 success, 1 general failure ("auth error, invalid
args, operation failed"), 3 MCP startup failure (only with
`--require-mcp-startup`, not used), 4 agent not found. Quota, rate-limit and
model errors have no code of their own, and `runError` has no structured
cause: only a free-text `message`. The plugin therefore maps every `runError`
and every nonzero exit to `NonzeroExit` (HTTP 502), without matching text.

**Not logged in hangs.** With an empty scratch `HOME` (no Kiro login; no model
call, no real account involved, nothing completed), `--no-interactive` still
starts a device-code login: it prints a blank line, then
`Confirm the following code in the browser`, a code and a URL on stdout, and
waits. The check was stopped by `timeout` after 40 s. In Pumice this shows as
`Timeout` (HTTP 504) once the provider timeout runs out. If the CLI ever
exits after printing that prompt, the plugin classifies it as `NotLoggedIn`.
The prompt text is matched only on a line that is not a JSON event, so model
output can never trigger it.

## Engine choice

Live calls 1 and 2 ran the same request on both engines:

| Engine | Time | Stream |
| --- | --- | --- |
| V2 | 3.1 s | `runStarted`, `metadata`, text chunks, `runFinished` |
| V3 | 5.1 s | Also mode/command/config updates, a `fetch_cloud_config` tool call, remote-session and content-collection logs on stderr, a KAS (Node) server start; the context breakdown still listed ~5.9k tokens of built-in tool definitions |

V2 is faster, simpler and quieter, and is the 2.x default, so it is pinned.
**Limitation:** `--help` calls V2 "the pre-3.0 default". If CLI 3.0 drops V2,
the plugin will need a V3 recipe (V3 also reads hooks from the workspace,
turns knowledge and code intelligence on in headless mode, and treats
`--trust-tools` as exact internal tool ids).

## Effort

`--effort` levels depend on the model ([effort]): the Claude models list
`low` … `max`, and GPT-5.6 Terra/Sol/Luna also list `none` (default `high`).
Models without reasoning (for example `claude-haiku-4.5`) print
`[warn] failed to set effort 'low': model does not support additional fields`
on stderr and run normally (live calls 1, 3 and 4). The plugin always passes
`low`, like the Codex plugin: it is the lowest level every reasoning model
accepts. **Limitation:** for GPT-5.6 models `none` would be cheaper, but
passing `none` to a Claude model is not a supported level, so a single value is
used rather than a per-model table.

## Models and cost

`kiro-cli chat --list-models --format json` (no chat call) lists `auto` and
the model ids with a credit multiplier. Among them: `claude-haiku-4.5` (0.4×,
no reasoning), `deepseek-3.2` and `minimax-m2.5` (0.25×), `gpt-5.6-luna`
(0.6×), `claude-sonnet-4.6` (1.3×). The plugin passes whatever the YAML
`model` says; it ships no default. Credits per live call were 0.006–0.014.

## Residual risks and limitations

* **Session history:** V2 saves every run under the user's own
  `~/.kiro/sessions/cli/<session id>.json(l)`, including the dictated text.
  There is no per-run switch; Pumice does not touch `~/.kiro`. (Same kind of
  residual as Kimi.)
* **Hooks and MCP from the user's profile:** the agent file sets no hooks and
  no MCP servers, and `tools: []` leaves the model no tool to call. Whether
  V2 still starts servers from a user `mcp.json` despite `includeMcpJson:
  false` was not observed (this account has none).
* **No error classes:** login, quota and rate-limit failures are all HTTP 502
  (`NonzeroExit`), or 504 for the login hang.
* **Engine pin:** see [Engine choice](#engine-choice).
* **Effort:** see [Effort](#effort).
* **Kiro's own base instructions** always sit under the client's system prompt.
