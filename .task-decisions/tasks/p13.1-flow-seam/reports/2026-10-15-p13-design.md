# P13 design: a local warm stack for dictation clients

Design proposal, 2026-10-15. Inspected `/home/brasillero/dev/personal/pumice`, main at `056627d`.
Author role: analyst/designer. No repository files changed; no AI CLI or model executed.
Recommendations below require the supervising orchestrator's decisions; they are not new owner decisions.

## 1. Recommended scope and decision precedence

Add `pumice serve [--config FILE] [--port PORT]`. It serves a separately enabled frontend on `127.0.0.1:17570`, embeds the existing relay and formatter libraries, and owns exactly one warm `pumice-transcribe serve` child bound to `127.0.0.1:0`. A UI submits audio plus an explicit flow and receives raw and final text separately.

Keep `pumice run` as a one-shot command using its current file subprocess transport. Keep independent module commands usable. P13b changes the browser client/proxy; P13 supplies its contract. No recorder, UI assets, hotkeys, paste, model downloader API, external-component attachment or deployment work in P13.

Precedence:
- `arch-modules/D1,D8,D13,D14`: independent module CLIs, CPU/GPU evolution, static core without the transcription crate, loopback only. D13 and P12/D1 supersede the old research proposal to spawn a relay process.
- P10/D1–D4: `relay.yml`, trusted real-executable sibling resolution, and explicit module dispatch. Use `--config`, following P12/D6, rather than the architecture plan's older `--stack-config`.
- P11/D1–D5: apply only selected instructions; preserve raw request values; retain conflict policy.
- P12/D1–D10: literal transcript boundary, overall deadlines, raw/final separation, no replay and no transcript persistence.
- P6/D3–D5: one inference, immediate busy rejection, successful empty transcript, resident model.
- P6/D6 says **every HTTP endpoint must match OpenAI**. The approved architecture and item 6c explicitly propose custom dictation/status endpoints. **Approval needed:** scope D6 to endpoints with an OpenAI contract and authorize versioned Pumice endpoints where there is none. Do not present a custom dictation response as an OpenAI transcription response.

Never inspect, stop, adopt or relocate the existing 7567 listener/service/tunnel. Ignore `relay.yml`'s server port when embedding its pipeline; no relay listener is created. Reserve 7567 out of the frontend's accepted explicit ports too, with a located config/argument error. An occupied frontend port fails; never select a different public port silently. Port 0 is allowed explicitly for tests/development and must be announced. No production ports were probed.

## 3. Why retain one warm child?

User-supplied server-1 measurements: portable inference 21.7 s, accelerated inference 5.9 s, cached load about 0.36 s, Claude/Haiku about 2–3 s. The CPU build difference dominates inference; a warm server does not explain that improvement. Cached loading is about 6% of a 6.2 s raw one-shot and about 4% of an 8–9 s formatted flow. These are rough comparisons, not controlled p95 measurements.

A warm child still fits the requested repeated-use service: loaded readiness is explicit, requests avoid repeated process/model initialization, and future GPU initialization can remain outside request latency. It already exists as a standalone module and the owner accepted its approximately 1 GB resident cost (P6/D5). Keep it for service lifetime; no idle eviction, pool, predictive preloading, automatic model switching or per-request file fallback. This removes policies rather than adding them.

**UNVERIFIED:** cold-page-cache latency, GPU initialization, spawn cost, long-running memory stability and warm-vs-cold p95 on any platform. Do not promise a speedup beyond removing repeated initialization. No benchmark or cache eviction was run for this report.

## 4. Topology, startup and ownership

The frontend is the only public stack listener. Its raw chat route calls the relay library in-process; its raw transcription route forwards to the owned child; its dictation route calls the child, then the same formatter/relay stages as `run`. All internal HTTP destinations are constructed from a validated numeric IPv4 port, never request content or arbitrary URLs.

Startup sequence:
1. Install Ctrl-C/SIGTERM handlers once, before loading/spawning. Reuse P12's signal registration, with service and per-operation cancellation reasons separated; a dropped client is not a synthetic Ctrl-C.
2. Load strict orchestrator/module references. Reuse relay/formatter loaders and transcription `models list --json` validation (5 s cap). When dictations are enabled, validate all enabled served flows, their model files, routes and formatters before inference or any paid call; otherwise validate only dependencies of the enabled raw endpoints. No login probe, CLI detection call or model download.
3. Validate the explicit served model and require every enabled served flow to use it. Fail at its flow field on a mismatch; disabled flows may use other models. `run` still supports its per-flow selections. One model avoids a hidden scheduler/model pool.
4. Bind frontend loopback early to claim its configured port. Until ready, metadata works and compute requests get safe 503. Fail immediately on bind/config errors and clean up anything owned.
5. Resolve the canonical sibling with `dispatch::sibling_transcribe`; spawn directly through `ProcessTree`, never shell/PATH/npm wrapper. Pass absolute config, `serve --model ID --port 0 --managed --instance-id ID`. `--managed` is a proposed orchestration mode, not present today.
6. Keep piped stdin open as an ownership lifeline; EOF requests child shutdown. Use stdout for bounded managed lifecycle JSONL; continuously drain/discard stderr. Start the child's shutdown/lifeline watcher before blocking model load, so an early shutdown cannot strand it indefinitely.
7. Await a ready announcement within 60000 ms. Then verify `/ready` against the same instance, protocol, product version, served model and required capabilities. Allow at most 4096 bytes per control line, a fixed small number of lifecycle records, and bounded metadata responses; refuse malformed/duplicate ready or unexpected control output. Never parse the existing human stderr line.
8. Build/publish one immutable runtime snapshot; mark available flows ready. No hot reload in P13. Emit a frontend ready record, including its actual port, after verification.

Proposed child ready record:
```json
{"schema_version":1,"event":"ready","module":"transcription","instance_id":"opaque-generation-id","protocol_version":1,"version":"0.2.0","host":"127.0.0.1","port":49152,"model":"turbo","capabilities":["openai_transcriptions","detailed_transcriptions","managed_shutdown"],"model_load_ms":362}
```

The ID is parent-generated metadata identifying a launch, not an authentication secret. Each replacement gets a fresh ID. Verify fixed host, nonzero child port, equality with expected instance/model, exact initial package version, and protocol/capabilities. Native backends remain governed by transcription's bundle compatibility. Do not log arbitrary received identifiers/labels before validation. An unexpected URL/host or redirect is a protocol failure.

`/ready` and the detailed transcription route exist only in managed child mode. Managed HTTP accepts the actual literal loopback Host and rejects any browser Origin header; core strips Origin only after validating it at the public frontend. Listening already follows successful load; readiness additionally confirms its identity and shutdown state. The private port is not a security boundary against other local processes; do not describe it as authenticated.

On missing binary, unsupported managed mode, incompatible protocol/version, invalid config or startup failure: tear down the child and exit nonzero with a fixed error and any trusted config location. Initial startup does not loop forever. Once ready, a child failure degrades transcription/flows and enters bounded recovery while frontend metadata/raw chat remain alive.

Runtime recovery proposal:
- States: `starting`, `ready`, `restarting`, `failed`, `stopping`; a monotonically increasing generation rejects stale replies/probes.
- Observe owned-child exit continuously. A 1 s liveness probe with 500 ms deadline, at most one probe outstanding, catches an unresponsive HTTP loop; three consecutive failures recycle the owned child. Busy inference is healthy and is not a probe failure.
- Restart after 0.5, 1 and 2 s, at most three attempts per failure episode; each attempt has the startup deadline. Reset the episode only after 60 s continuously ready. Exhaustion leaves state `failed`, no further timer; operator restarts `pumice serve` after repair.
- Deterministic protocol/version/config errors stop recovery immediately. Always kill/reap the previous generation before starting another; no overlapping model copies. Keep unreaped ownership and report cleanup failure rather than grow an unbounded list.
- Recovery never replays the failed HTTP request, inference or paid call. No fallback provider, model or external service.

Shutdown: set stopping/unready, stop admission, cancel all owned operations/probes/restarts, close child stdin for cooperative stop, and finish existing response/cleanup paths within a 5000 ms service budget (2500 ms grace, up to 2000 ms force-kill/reap, remaining output reserve). After grace, call existing tree/scope teardown and bound HTTP connection drain; do not await native drain forever. Exit 130/143 for the initiating signal, or 1 for fatal cleanup/runtime failure. Only retained owned handles are signalled, never processes discovered by ports/names.

On parent death, stdin EOF should make the child cancel and exit; managed mode needs its own bounded shutdown watchdog because native cancellation can stall. A hard-exit fallback is confined to this transcription process after grace. Windows Job Object kill-on-close supplies an additional defense. **UNVERIFIED:** abrupt-parent-death behavior and console signal delivery on Windows/macOS; require fake-process tests and retain P12's explicit manual-platform caveat.

## 5. HTTP contracts and official OpenAI check

Official reference pages fetched on 2026-10-15:
- [Create transcription](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create): multipart file/model input, optional controls and format-dependent output.
- [Create chat completion](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create): model/messages, completion objects, optional SSE chunks.
- [List models](https://developers.openai.com/api/reference/resources/models/methods/list): OpenAI model objects inside an `object:list` response.
- [Error codes](https://developers.openai.com/api/docs/guides/error-codes): HTTP failure classes; quota and rate limiting use 429, service availability can use 503.

These define shapes, not Pumice's local model names, admission policy, custom endpoints or native deadlines. Pumice supports a documented subset; it is not the full OpenAI service. Local upload/time limits and proxy failures below are Pumice policies.

### Ordinary routes

`POST /v1/audio/transcriptions`: raw STT only. Preserve child request bytes/multipart boundary, supported options, HTTP status, response bytes and content type. Required `file` and exact served `model`; optional `language`, `prompt`, `temperature`, `response_format=json|text`, absent/false `stream`. Unknown/duplicate/unsupported fields get 400. Never accept flow/formatter/provider selectors here. JSON remains `{"text":"..."}`; text remains exact text; successful silence remains empty. Do not invent language/usage/timing fields in this response. Supported codecs remain the child's compiled subset, including WebM/Ogg Opus when available; AAC/MP4 remains unsupported.

`POST /v1/chat/completions`: compose the existing relay handler/router in-process; no implicit formatter and no transcription dependency. Preserve the existing prompt/extraction, final cleanup and JSON/SSE contract. The relay supports text input, one user message plus instruction messages, and model route selection. Document that its SSE is emitted after completion, not token progress.

There is a verified D6 gap: existing chat silently ignores unsupported OpenAI controls. Recommend a reusable **strict request validation mode in the relay library**, selected only by the new stack frontend: explicitly reject unsupported fields/content/options with safe 400 before provider execution; preserve accepted bytes and messages. Keep standalone relay behavior/Handy fixtures unchanged. This is a deliberate scoped validation change needing supervisor approval. Do not claim full option support or silently normalize client input. New frontend errors must not echo unknown route strings (existing relay errors can name them).

`GET /v1/models`: one stable OpenAI-shaped union of the served transcription ID (when STT/dictations enabled) and embedded relay IDs (when raw chat enabled). A configured/loadable transcription model remains listed during restart; status describes availability. Never list formatter/flow IDs as models. Reject cross-module ID collisions at startup rather than prefixing/rewriting IDs. No network or model work to list them. Provider routes retain their existing IDs; `owned_by` can distinguish `pumice-transcription` and `pumice-relay` without extra object fields. `created:0` follows existing local precedent.

`GET /v1/models/{id}`: same objects and safe 404 for unknown IDs; add relay retrieval using the shared model-object builder, without inventing another lookup system. Metadata discovery never means provider login/quota was checked.

Only exact documented routes are forwarded; no arbitrary proxy path, target parameter, redirects, environment HTTP proxy or outbound DNS. Hop-by-hop headers are stripped, Content-Length is recomputed when necessary, and incoming Host is replaced with the owned loopback authority. Remove the already-validated browser Origin before internal forwarding. Authorization headers are unnecessary and need not be forwarded to the child; never pass them to a provider CLI.

### Custom dictation request

`POST /pumice/v1/dictations`, multipart/form-data, synchronous JSON response. Exactly one uploaded nonempty `file` and one text `flow`; flow ID must exactly name an enabled configured flow. Allow either order. Reject duplicates, unknown parts, non-UTF-8/NUL scalars and file-valued `flow`. Do not accept paths, URLs, model/rule overrides, client prompt, arbitrary commands or `stream`.

The flow chooses model/formatter/relay route from config. Transcription options inherit `transcribe.yml`; per-request language/prompt overrides can be a later explicit extension. A language-specific future flow needs a designed configuration reference, not hidden instructions or automatic translation. Raw OpenAI transcription retains its own client controls.

Audio is never written to a filesystem path derived from its filename. Prefer one bounded in-memory byte buffer and rebuild only the internal multipart framing, preserving file bytes; no temp audio file is needed. Core does not sniff/decode codecs or duplicate transcription validation.

### Custom result and partial failure

Use the schema-1 `RunEnvelope` success shape. `module:orchestrator`, opaque operation ID, `ok`, selected flow, `transcript`, success-only `result`, all four stages, and `timings_ms.total`. `prepare` now measures request/flow preparation, not daemon startup. `elapsed_ms` includes the stage's transport/setup work. Omit unavailable optional timing values instead of inventing zeroes.

Example success (illustrative timings):
```json
{"schema_version":1,"operation_id":"op-id","module":"orchestrator","ok":true,"flow":"clean","transcript":{"text":"raw words","language":"en","audio_seconds":2.1},"result":{"text":"Raw words."},"stages":{"prepare":{"status":"ok","elapsed_ms":2},"transcription":{"status":"ok","elapsed_ms":5900,"inference_ms":5800},"formatter":{"status":"ok","elapsed_ms":1},"relay":{"status":"ok","elapsed_ms":2400}},"timings_ms":{"total":8303}}
```

For HTTP failures, keep P12 fields and enrich its error with OpenAI-style `message,type,param,code`; retain `stage,retryable:false,cause_code,location` as custom-route extensions. This avoids two competing error objects. Reuse a common error classifier/serializer with CLI-specific vs HTTP-specific presentation; do not silently change P12 JSON. Every custom-route rejection, including pre-body 429/503 and malformed uploads, uses this versioned envelope: omit flow when it could not be safely selected, mark prepare error when attempted, and leave later stages skipped. No HTTP error message quotes user-supplied flow IDs/field names, transcripts or raw child output.

Example provider failure, HTTP 502 (the real response includes all four stage reports/timings):
```json
{"schema_version":1,"operation_id":"op-id","module":"orchestrator","ok":false,"flow":"clean","transcript":{"text":"raw words","audio_seconds":2.1},"error":{"message":"The provider returned an unusable reply.","type":"server_error","param":null,"code":"relay_invalid_output","stage":"relay","retryable":false}}
```

`result` is absent on any failure, including cleanup failure. Raw text is retained once successfully transcribed, also on formatter/provider timeout/error or later server shutdown. Whitespace-only raw text succeeds unchanged, with downstream stages skipped. No HTTP 200/206/207 partial-success convention and no raw-text substitution as final output. Clients must read JSON on non-2xx to recover the transcript. No recovery storage/get-by-operation endpoint; a lost response cannot be fetched later.

### Internal detailed transcription seam

Add managed-only `POST /pumice/v1/transcriptions` in the child. Reuse its exact multipart parser, limits, admission, cancellation worker and service, then serialize its existing CLI-style versioned detailed result: raw text, language when known, audio_seconds, inference time. Measure inference at the service seam; do not label decode+inference as inference. Failures use safe code-bearing errors; version and shape validation occur in core.

This route is called only for dictations; the public frontend never forwards this path. It solves the required duration/language/timing gap without changing OpenAI JSON. Do not infer duration in core, put text in headers, or expose fake `verbose_json`. Parent response cap is 1 MiB, including envelope. Omit per-request model_load_ms for a warm request; startup load belongs in child status, once per generation. Keep the plain `run` metrics as today.

### Status codes and bounds

The mapping below applies to custom dictation errors and new frontend failures. Ordinary raw routes retain module error statuses (for example, existing relay missing/login failure is 502); strict frontend validation does not silently change standalone relay behavior. Apply OpenAI error-object fields to ordinary-route errors; custom errors additionally use the flow envelope. Return JSON on all framework rejections too, including 404/405, with `Allow` on 405. No HTML framework errors.
- 400 `invalid_request_error`: malformed/duplicate/unsupported fields, codec/decoded-duration errors, disabled flow. 404: unknown flow/model/URL, with fixed safe message. 403: browser-origin/Host rejection.
- 408: upload deadline. 413: byte/scalar limits. Keep current STT unsupported-codec 400, not a new 415 policy.
- 429 `rate_limit_error`: local busy admission or provider rate/quota error. Local busy adds `Retry-After:1`; provider delay is forwarded only if known, never fabricated.
- 503 `server_error`: child starting/restarting/failed, service stopping, provider CLI missing/not logged in. Provider credentials belong to the server, so do not answer 401 as though the frontend caller needed an API key.
- 502 `server_error`: child crash/broken protocol/transport or relay failure/invalid output. 504: processing/flow timeout. 500: unexpected frontend failure, child engine failure, or cleanup failure. Ordinary STT preserves its existing child's typed HTTP status; transport failures are mapped safely.
- Cancellation from a disconnected client sends no fictional HTTP 499 response. A still-connected request cancelled by shutdown gets 503 with any completed transcript, if response time remains.

Limits: inherit 25,000,000 file bytes, 26,000,000 complete multipart body bytes (including epilogue), 16 KiB per scalar, and 120 decoded seconds. Dictation `flow` gets a tighter 128-byte bound; validate configured IDs that can be served to the same bound. Known parts restrict part count naturally (two for dictation; seven for existing STT). Never buffer unbounded unknown fields or chunked epilogues. Do not add the dev helper's Content-Length requirement to the frontend.

Chat retains 10 MiB body/5 s upload limits. Audio endpoints have 15 s arrival-to-upload-complete. Reject oversized declared Content-Length early and count real bytes regardless of headers/chunking. Child detailed output is capped at 1 MiB; final combined serialized response is capped at 16 MiB. If final text cannot fit, fail `relay_invalid_output` with cause `output_too_large` and preserve the bounded transcript; never truncate it. This is a proposed additional HTTP output policy.

## 6. Admission, deadlines, cancellation and failure isolation

Recommend **one shared work permit across dictations, raw STT and raw chat**, acquired before reading any body; busy means immediate 429, no waiting queue. Metadata never needs it. Hold it through upload, stages and cleanup, not just inference; this bounds uploads, memory, paid calls and shared cleanup ownership. It deliberately serializes a raw request behind a whole dictation for this first version. Standalone services retain their existing policies; separate `run`/live relay instances do not share this limiter.

Use one service-lifetime embedded pipeline, provider pool and service-owned `CleanupScope`. Under this single permit it is safe to drain that scope between requests: no other request owns provider resources. Never rebuild the pipeline per request and accidentally bypass module concurrency. A later concurrency increase requires request-scoped cleanup ownership first. If cleanup cannot confirm teardown, mark work admission unavailable and retry only cleanup in bounded shutdown/recovery; do not start a second paid call over uncleared resources.

Request clocks start at accepted request arrival, including upload. For a dictation, its flow is learned while parsing, but total is still anchored to arrival: after parse, compute `arrival + total - 2500ms`, never reset at stage boundaries. Because file and flow may arrive in either order, a selected flow can otherwise have a shorter total than time already spent uploading. Bound dictation preparation by `min(15s, minimum enabled served flow total minus 2500ms)`, anchored to arrival, until selection is complete. This conservative bound prevents a flow arriving last from retroactively violating its advertised deadline; one unusually short flow reduces the shared upload window and should be documented. When a flow cannot be selected before this bound, return 408. If selected total is already exhausted for another reason, fail before child/provider work. Stage deadline is min(remaining flow work deadline, stage cap); modules can shorten it. Keep P12's timeout classification/caller-bound reserve handling. Never start a paid call after the deadline or accept a late success.

Default raw STT arrival-to-response cap is 120 s; raw chat uses relay.yml's total/provider budgets. Any outer cleanup reserve can only shorten them. Dictations use P12 flow defaults and its 2500 ms cleanup/output reserve; existing child's 120 s module cap can shorten a longer configured STT stage. Startup/restart has its own lifecycle clock and does not consume a queued request budget because requests are rejected while unready.

Use service cancellation plus per-operation cancellation/drop guards. Cancellation must stop the operation future, not merely return a timeout from an outer wrapper while spawned work continues. During provider work, drop its future, then await bounded scope drain; never replay or switch provider. Protect the operation guard so cancellation of the HTTP handler schedules cleanup under the supervisor and retains the work permit until that cleanup finishes.

For transcription abandonment after dispatch (timeout/disconnect/shutdown), close the upstream request and **recycle the owned child generation** rather than assume its cooperative native cancellation has completed. Its process is exclusively serving one admitted audio operation. Force-kill/reap within the cleanup reserve, then recover separately; no replay. This sacrifices warmth on exceptional paths but gives a clear resource bound without a job/cancel/ack protocol. Do not kill an idle child when cancellation happens later in formatter/relay. A completed raw transcript survives a subsequent child crash; the current relay stage can finish independently.

**UNVERIFIED transport behavior:** existing tests cancel router tasks (`request.abort()`), not real TCP sockets. Axum handler-drop assumptions alone do not prove disconnect cancellation after upload. P13 must test real socket reset/close during upload, inference and provider execution. If the server does not drop the operation on reset, use a small connection driver with a connection-lifetime cancellation token (HTTP/1, no request work detached from it), preserving legitimate write-half-close semantics; do not ship a claim based only on in-process abort tests. Internal child disconnect uncertainty is contained by explicit recycle. Browser proxy cancellation is separately end-to-end work in P13b.

Unexpected request-task panic must run the same ownership guard/cleanup before releasing admission; use sanitized panic reporting and safe internal errors. Do not let default panic payloads log request content. Native abort/segfault is isolated to the child. An abort/panic in the in-process relay/core remains a core failure: no complete crash isolation is promised. Close the parent-lifeline and retain Job Object/process guards. Existing P12 panic and manual Windows/macOS caveats remain open until specifically tested.

## 7. Status, readiness, flow discovery and events

Smallest useful UI contract: one synchronous dictation POST, one flow list and a cheap status snapshot. Defer SSE/WebSocket events, asynchronous jobs, transcript history and operation polling. P13b can show a spinner and elapsed client time while awaiting final raw/final fields; it cannot show raw text before relay finishes. Early raw delivery would need a later streaming/job contract.

- `GET /health`: 200 `{status:ok,version:...}` while the frontend loop is alive, independent of child/provider state. No dependency probes triggered by the request.
- `GET /ready`: 200 only when all enabled endpoint dependencies are locally initialized and service is not stopping; otherwise 503 with an OpenAI error. Busy still means ready. Availability of individual routes/flows is in status, so raw chat remains usable during a transcription outage. Readiness never means CLI login/quota was checked.
- `GET /pumice/v1/flows`: schema 1, enabled flows only, with `id`, configured transcription model/formatter/relay route and coarse `ready`/safe unavailability code. No formatter rules, paths or disabled-flow details. No implicit/default flow; client must select. Fail startup if more than 128 served flows or IDs exceed 128 bytes; no silent truncation.
- `GET /pumice/v1/status`: schema 1, instance/version, service state, active-work boolean and coarse current stage, child state/generation/restart-attempt count/next retry delay, served model/startup load time, dependency availability and enabled-flow count. Omit operation IDs/content, config paths, stderr, provider diagnostics and private child address. No completed-request list or unbounded counters/history.

Status/health/flows read immutable/atomic local state, make no network/CLI/model calls, and never await the work permit. Bound output to 128 KiB and serialization/request handling to 250 ms; cap accepted metadata connection/request concurrency separately so polling cannot create unlimited tasks. Cap total frontend connections (e.g. 64) and idle/header-read time (5 s); rejecting excessive connections need not create additional queued work. Polling recommendation: status at most once per second while active, slower while idle; flow list once per session or refresh.

Use P12's event sink abstraction for metadata-only stage updates to the snapshot and optional service stderr JSONL (`pumice serve --json`). No per-request writer thread; use one bounded service writer, capacity 64, drop under backpressure, cap each line to 4096 bytes, bounded drain. Stdout under --json carries bounded lifecycle records (ready/stopped/error) and no HTTP result content; plain mode announces the frontend URL on stderr. A stalled output consumer must never block requests/shutdown. Child control parsing and required startup reads are separate bounded channels, not lossy progress events.

## 8. Configuration proposal

Extend schema 1 additively; existing `run` files without `serve` remain valid. `serve.enabled` defaults false, endpoint booleans default false, and invoking `serve` with no enabled frontend/endpoints is a located error. Enabling dictations requires at least one enabled flow. Explicit flags do not silently enable a module/endpoint. The command is explicit; keep bare `pumice` as overview/exit 2 in P13, pending a separate default-command decision.

```yaml
schema_version: 1
modules:
  transcription:
    config: ./transcribe.yml
  formatter:
    config: ./formatter.yml
  relay:
    location: in_process
    config: ./relay.yml
serve:
  enabled: true
  port: 17570                  # optional built-in default; never inherited from relay
  transcription_model: turbo   # explicit when audio/dictation endpoints are enabled
  startup_timeout_ms: 60000    # optional default; validate 1000..300000
  endpoints:
    transcriptions: true
    chat_completions: true
    dictations: true
flows:
  - id: raw
    enabled: true
    transcription_model: turbo
    formatter: null
    relay_route: passthrough
  - id: clean
    enabled: true
    transcription_model: turbo
    formatter: builtin:clean
    relay_route: claude
    # Optional budgets_ms retain P12 defaults and validation.
```

`transcription_model` is a routing/ownership selection, not a model definition. Model paths, language/threads/backend, providers/CLI binaries/models/reasoning/timeouts/debug settings and formatting rules remain only in their module files. Child port is always 0 because orchestrator owns its location; it overrides standalone `transcribe.yml.server.port` explicitly. No external URL/binary-path alternative in P13; keep trusted sibling semantics. No frontend host field, auth keys, CORS wildcard or child port knob.

Launch only dependencies of enabled endpoints: STT for audio/dictations, relay for chat/dictations, formatter only if a served flow selects one. Existing required module-reference parsing may stay required; unused modules need not start or initialize native code. ## 9. Security, privacy and browser integration

Bind fixed IPv4 loopback only, including all fakes. No authentication for this local iteration, consistent with D14; loopback does not isolate other local users/processes. Use direct internal HTTP with no redirects/proxy environment support. No credential files, login action, shell interpolation, request-selected paths or generic HTTP forwarding.

Reject unexpected Host authorities to limit DNS-rebinding use: accept literal `127.0.0.1` with the actual listener port (and normal HTTP/1 authority rules), not arbitrary DNS names. Apply an Origin guard before admission/body consumption: absent Origin is permitted for native clients; present Origin must exactly match this listener's own `http://127.0.0.1:PORT`. Reject `Origin:null`/file pages, localhost aliases and other origins with 403. Reject cross-site fetch metadata when present. No `Access-Control-Allow-Origin:*`; CORS absence alone is insufficient because multipart requests can be sent without preflight.

For P13b, prefer the existing same-origin Python helper, explicitly pointed to `http://127.0.0.1:17570`. Extend its exact route allowlist to `/pumice/v1/dictations`, `/pumice/v1/flows`, `/pumice/v1/status` and needed `/v1` routes. Validate browser Host/Origin against the helper's own literal loopback origin, then remove the already-validated Origin before server-to-server forwarding. Merely forwarding the 17569 Origin would correctly be rejected by the frontend; blindly stripping it without checking would bypass the guard. No P13 CORS exception is needed.

P13b must raise the current helper/page 135 s timeout to cover configured flow total plus a small transport margin (default e.g. 190 s for 180 s), and prove AbortController cancellation closes upstream promptly. The current blocking proxy only learns a browser disconnect during response writes, so end-to-end cancellation is **UNVERIFIED and likely needs proxy changes**. Do not advertise cancel support through it until tested. Direct native clients exercise the P13 contract independently.

The helper currently documents optional Tailscale exposure. P6/D8 keeps transcription local-only; P13b must document loopback-only use and must not enable/configure Tailscale/tunnels or treat that historic example as authorization. Direct browser/file mode remains unsupported unless a later explicit-origin policy is approved. An HTTPS page on another machine cannot make its own 127.0.0.1 refer to server-1.

No audio/transcript/result/request body in ordinary logs, status, events, panic payloads or child stderr forwarding. Do not derive Debug on new content-bearing types. No request filenames/unknown field values in errors; log only bounded verified metadata. Keep `Cache-Control:no-store` on result/status/discovery responses and no response-body access logging. Clear sensitive in-memory buffers by dropping them after response/cleanup; secure zeroization is not claimed.

## 11. Open questions for the supervising orchestrator

These are the complete proposed decision points; none is recorded as approved here.

1. **Custom endpoint authorization versus P6/D6?** Recommend explicitly limiting OpenAI compatibility to routes with an OpenAI equivalent, allowing versioned custom dictation/status/managed metadata. Record this clarification before implementation.
2. **Command/default behavior and port?** Recommend explicit `pumice serve --config`, leave bare-command overview unchanged for P13; frontend default 17570, explicit enablement, 7567 forbidden, port 0 only when explicitly chosen. No service/tunnel migration.
3. **Warm lifetime worth the RAM?** Recommend exactly one child for service lifetime, accepting existing approximately 1 GB cost. No cold fallback, idle unloading or performance claims from cached-load data alone.
4. **Multiple flow models?** Recommend one explicit serve.transcription_model and startup rejection of any enabled served flow selecting another model. P13b picks among raw/formatting/provider flows over the same audio model. Multiple resident models/model switching need a later design.
5. **Managed control and wire compatibility?** Recommend stdout lifecycle JSONL, stdin EOF shutdown, managed-only readiness/detailed endpoints, protocol 1 plus required capabilities and exact package version initially. No external attachment/custom binary path.
6. **Recovery policy?** Recommend three post-readiness restarts, 0.5/1/2 s backoff, 60 s stable reset, 60 s startup default (configurable to 300 s), no startup retry for invalid protocol/config. Keep frontend/raw chat alive while STT is degraded.
7. **Whole-operation admission?** Recommend one shared permit for all work routes, immediate 429/no queue, retained through cleanup. Independent raw-chat/STT overlap can follow only with resource-scoped cancellation/cleanup.
8. **Partial failures and HTTP error extensions?** Recommend non-2xx with raw transcript, no final result, OpenAI-style error fields plus custom stage/cause/retryability fields. Preserve P12 CLI schema; clients parse error bodies. No persistent recovery or automatic retries.
9. **Request cancellation when native STT stalls?** Recommend recycle the owned child on abandoned in-flight STT, inside the request cleanup reserve; verify real socket resets and parent-death paths. Native half-close/cancel behavior must be experimentally resolved with fakes, not assumed from handler-drop tests.
10. **New-frontend chat strictness versus existing relay behavior?** Recommend explicit unsupported-option rejection in a composable relay validation mode, preserve standalone Handy behavior. Existing unknown-field ignoring is a verified D6 exception; supervisor must authorize its scoped resolution rather than conceal it.
11. **Discovery model namespace?** Recommend union of STT and raw-chat models, exact original IDs, startup collision errors, metadata availability in status, flows in a separate endpoint. No automatic ID prefixes or disappearing IDs on temporary failure.
12. **Dictation options and limits?** Recommend only file+flow initially, inherit module language/settings; P6 audio/upload limits plus the conservative preselection flow deadline, 128-byte IDs/128 flows, 1 MiB STT result and 16 MiB combined HTTP result. Approve these tighter serving/output bounds; report oversized results safely rather than truncate.
13. **Events and early transcript?** Recommend polling status and synchronous POST only. P13b receives raw and final together; early raw display/stage event streaming is deferred. Bounded existing-style metadata stderr remains available.
14. **Browser policy?** Recommend exact frontend same-origin guard, no cross-origin CORS grants, P13b validated same-origin helper proxy with explicit stack upstream. No file:// or remote/Tailscale exposure. Proxy disconnect propagation is a P13b acceptance gate.
15. **Shutdown and panic contract?** Recommend 5 s service shutdown, force owned trees after grace, bounded child EOF watchdog, metadata-only panic reporting, no false native/core crash-isolation promise. Windows/macOS manual checks remain explicitly UNVERIFIED until performed.
16. **Config breadth and release/implementation order?** Recommend additive strict serve section, explicit per-route booleans, existing module references and flow budgets, no general managed/external schema or hot reload. Land five PRs above; keep P13b and any packaging/GPU/performance work separate. The supervisor chooses release version/deployment independently; no release is authorized by this design.
